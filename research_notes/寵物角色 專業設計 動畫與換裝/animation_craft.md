# 手機養寵角色動作與互動：專業動畫製作研究

研究日期：2026-10-19。範圍：動畫表演與實際互動；不評角色造型、不改程式。本筆記中的「本案提案」都是設計推論，並非訪談者替我們背書。以下各來源工具標示的摘要上限皆為 200 words／頁；最終報告應擇要轉述，避免把同一來源重複寫成多個長段落。沒有看完影片，只核對官方文字 breakdown；不得寫成已觀看完整影片。

## 為什麼只抬手、整隻縮放或一直晃動，會像技術展示？

### Takeaway

專業動畫師先建立動機、姿勢、重心、接觸與時間關係，再加次要動作。平滑插值本身不會提供「牠想吃、抓到了、用力了、滿足了」這些表演資訊。

### Cited Findings

- Wayne Gilbert，曾任 Disney、ILM、EA 動畫師，2017-09-06 在 Animation Mentor 的〈How to Create Believable Weight in Animation〉說明：重量靠姿勢、平衡、路徑與 timing 暗示；先決定為何動，再決定怎麼動。抬腳前重心須接近支撐腳，接觸時的壓縮與離開接觸時的抬升應有可讀的受力。— [原文](https://www.animationmentor.com/blog/how-to-create-believable-weight-in-animation/)
- Chris Hurtt，2017-06-07 在 Animation Mentor 的〈Anticipation〉說明：預備動作可以很微小，不只是永遠先朝反方向動；預備的時間、速度、幅度要配合後續動作，否則容易機械或落入套公式。— [原文](https://www.animationmentor.com/blog/anticipation-the-12-basic-principles-of-animation/)
- Nathaniel Seymour，作品含《Dune: Part 1》《Pokémon Detective Pikachu》，2025-10-10 官方教學拆解：先做好鳥的身體與頭部，再把尾巴延遲疊上去；注意輪廓、負空間，過度 overlap 會漂，過少則僵硬。— [教學摘要與影片入口](https://www.animationmentor.com/blog/tutorial-animate-overlap-and-follow-through/)
- AnimSchool 講師 Jarrod Showers 的 2018-06-08 idle 教學：動作應有性格與平衡；小動作太密、轉頭太頻繁會不自然；要檢查循環首尾曲線，避免接點跳動。— [教學摘要與影片入口](https://blog.animschool.edu/2018/06/08/4-quick-tips-for-a-better-idle-animation-cycle/)

### Inferences

- 本案不應用同一個全身縮放函式同時代表呼吸、開心、吃東西。這會抹平每個動作的動機與接觸差異。
- 待機提案：腳和接地影子穩定，胸腹呼吸比頭部明顯，尾耳不同拍；偶爾抓癢或調整坐姿，每次小動作後回到安靜姿勢。角色性格決定是害羞縮手、貪吃前傾或慢吞吞，不能只換配色。
- 摸摸提案：接觸哪裡，哪裡先回應；例如肩膀受碰先小幅下沉，再靠向手勢，耳尾稍晚反應。不能每次觸碰都整隻彈跳。
- 玩具提案：追玩具前有身體朝向與蓄力，碰到玩具有接觸停頓或反作用，抓到後道具跟著手；若沒有咬住／抓住的連接，玩具會像漂浮貼圖。

### Gaps

- 這些原文不是養寵 app 的 feed／petting 專門規格，不能假稱業界統一如此做。上述對本案的對應是我們推論，仍需以分鏡與動作預覽驗證。

## 真實 App 團隊如何把動畫作品變成可互動內容？

### Takeaway

Rive 的商業案例是動畫師親自設計時間軸，再用狀態機安排播放與互動；高品質 3D 養寵則還有手工動作、大量資產、IK、look-at 與裝置效能管線。選引擎不能取代動畫表演。

### Cited Findings

- Valerie Veteto，2024-07-25 Rive 訪談 Duolingo：具名受訪者包括動畫副創意總監 Alex Chopjian、creative technologist Jeff Masters 等。流程為動畫師做 Rive motion graphics／timelines，creative technologists 協作進階 state machine、撰寫 inputs 規格，再交互動資產給工程師；Rive 資產本身直接進產品，減少工程師重寫外觀的落差。— [完整訪談](https://rive.app/blog/creative-technologists-duolingo-s-solution-to-the-designer-to-developer-handoff)
- Adam Axler（Unity），2025-11-25 訪問 Outfit7 的 fellow software engineer Mihec Pezdirc 與 principal software engineer Črt Kristl：My Talking Tom Friends 2 約有 1,000 段動畫；runtime 含 retargeting、IK、look-at。點擊拖曳使用輕量碰撞查詢，並非所有互動都靠完整物理。對話／招呼依行為、距離與 cooldown，避免重複。— [完整訪談](https://unity.com/blog/bringing-my-talking-tom-friends-2-to-life)
- Samy Ben Rabah，Outfit7 Senior Software Engineer，2024-10-07 說明：動畫師在 Maya 使用角色／道具 rig，做 IK、blend shapes 等動畫，再烘焙骨骼、移除不必要節點並匯出；概念、模型、rigging 是動畫前置任務。這是資產製作到產品整合的證據，不是 Rive 做法。— [Outfit7 第一人稱文章](https://outfit7.com/blog/tech/outfit7s-art-pipeline)

### Inferences

- 本案製作分工提案：插畫／動畫設計負責關鍵姿勢、動作意圖、弧線、接觸、節奏與收尾；Rive rig 與狀態機負責可重用的控制、混合、輸入映射與中斷；應用程式負責命中區、背包物品、餵食成立條件、資料儲存。
- 程式可以根據拖曳位置改變「靠近程度」，但不能讓未經設計的姿勢自動變有魅力；狀態數量與操作按鈕多寡也不是品質指標。
- 2D skeletal 提案：先畫關鍵姿勢、確認輪廓，再建骨架、樞紐與變形；避免每肢只像紙片旋轉，必要時另畫手掌、彎曲部位或替換姿勢。
- 逐格提案：由動畫師設計關鍵張、breakdown 與張數分配；程序只負責影格播放與狀態銜接。僅把一張圖分層搖動，不能稱作逐格製作。
- 3D 預渲染提案：仍先完成角色、rig 與有表演的動作；固定鏡頭渲染只改變交付格式，沒有免除造型、動作與接觸製作。若臉需另外疊圖，需每幀輸出頭部錨點並檢查遮擋。

### Gaps

- 沒有找到可核實 Finch／Neko Atsume 製作引擎或具名餵食動畫 breakdown 的一手資料；不應以畫風猜 Rive／Spine。
- Outfit7 訪談為工程人員視角，沒有公布每個餵食動作的動畫分鏡；近 1,000 段是該遊戲規模，不能當本專案的最低需求。

## 真人原照片臉不變形時，哪些表演仍然成立？

### Takeaway

本案若堅持單張照片五官不變，就應把動作限制納入表演設計；身體、手、耳尾與道具可以演出，無法憑空得到照片沒包含的嘴型或側臉。

### Cited Findings

- Nathaniel Seymour，2026-09-09 官方教學以「抓住、拉動、放開火柴」示範：道具在抓住的指定影格才啟用 parent constraint，釋放時解除；先確立手臂動作，再逐層加入脊椎、肩與頭部不同步的反應。這是維持接觸與動作層次的具體範例。— [原文與影片入口](https://www.animationmentor.com/blog/tutorial-animating-character-prop-interaction/)

### Inferences

- 本案保真提案：照片只做整體平移、小幅畫面內旋轉與等比縮放；不做非等比拉伸、嘴巴開合、臉頰膨脹、眼球移動或自動生成側臉。「等比縮放」仍可能降低顯示解析度，需在實際尺寸檢查。
- 單張正面照片不能靠橫向壓扁就變成可信的側臉。頭部維持正面，以肩膀前後、身體傾斜、耳朵與手勢表達方向。不能宣稱有真實 gaze tracking：可以讓頭部整體朝輸入方向微傾，但照片中的視線不會改變。
- 不做真人嘴巴咀嚼；改成兩手把餅乾送到臉前，短暫有自然遮擋，配合食物缺口／碎屑、身體節奏與滿足姿勢，傳達吃到。這是風格化暗示，需讓使用者看過再決定是否接受，不能說與嘴型動畫相同。
- 洗澡先限定可變形身體區；刷子行經處髒污逐步消退、接觸時軀幹小幅受壓、結尾甩手抖耳。照片臉不拿來做搓揉變形，也避免用大泡泡全程遮住臉掩飾問題。

### Gaps

- 本次未找到具有可信公開 breakdown、又同時符合「養寵身體＋單張真人臉全程零五官變形」的商業案例。因此以上全部是本案設計提案，非既有業界標準或已驗證解法。
- 單張照片的笑容固定；身體滿足但照片表情不配合時仍可能違和，不能靠技術承諾完全解決。

## 下一輪如何審核一個餵食動作，而非再做兩個空殼 MVP？

### Takeaway

先審核有起因、接觸、結果的短動作。把整段動畫暫停在關鍵姿勢，仍應看得懂角色正在做什麼；先驗收表演，再接背包或更多動作。

### Cited Findings

- Jarrod Showers 的另一篇 2018-05-21 AnimSchool 教學強調遊戲動作需要可讀的強姿勢；姿勢停留要足以讀懂，轉換可以快速；互動需及時響應，並考慮可中斷。— [原文](https://blog.animschool.edu/2018/05/21/what-makes-a-great-game-animator/)

### Inferences

以下為本案餵食 storyboard，全部時間為提案值，非業界標準；總長約 2.4 秒，另加使用者拖曳等待時間。

| 階段 | 提案時間 | 身體／道具表演 | 必須看得見的因果與驗收點 |
|---|---:|---|---|
| 注意到 | 0–0.2 秒 | 拖起食物即有小幅肩膀抬起、手掌張開；照片維持不變 | 有即時回應，不要等整段預備動畫才回饋 |
| 想吃／等候 | 拖曳期間 | 食物接近時身體前傾、手稍伸；拉遠則回到等待，腳仍有支撐 | 反應由食物距離決定，尚未成功時不可扣物品 |
| 接住 | 0.2–0.5 秒 | 放進有效區後雙手收攏，食物才由游標轉為手部附著 | 抓取前後食物位置連續，不能瞬移、穿掌或提早消失 |
| 送入口前 | 0.5–0.9 秒 | 手沿清楚弧線移到臉前，身體稍跟；耳尾稍晚跟上 | 手、食物、軀幹各可辨，照片沒有被拉長；不冒出不存在的嘴型 |
| 吃到的暗示 | 0.9–1.5 秒 | 食物在手／臉前遮擋時少一口，配合少量碎屑；肩胸有兩次克制節奏 | 食物減少與成功事件同拍；不能只加愛心就叫吃到 |
| 滿足姿勢 | 1.5–2.0 秒 | 手放下、一手輕碰肚子，身體放鬆；尾巴短促回應 | 與等待姿勢有明顯差異，能讀出結果 |
| 收尾 | 2.0–2.4 秒 | 主體先穩定，耳尾再收；回到相容的待機姿勢 | 不突然 snap 回起始、不持續彈簧晃動；腳不滑 |

本案評審提案：

1. 靜音、移除愛心與文字，仍能辨識「注意／接住／吃到／滿足」。
2. 暫停在接觸影格：食物與手／臉前區有合理遮擋，沒有漂浮或穿透。
3. 黑色剪影測試：手臂和道具不全疊在軀幹裡；在手機實際顯示大小可讀。
4. 原照片疊圖比對：五官比例不改，只有剛性變換；大幅側轉與假咀嚼視為不符需求。
5. 拖進再拉走、快速連按、動畫中再觸碰，均有明確恢復路徑；食物只在有效成功點消耗一次。
6. 連看多次時不出現循環跳動；待機安靜程度能容許看 UI，不一直搶注意。
